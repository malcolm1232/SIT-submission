# Human labelling protocol (one rater)

Date: 2026-10-02. Implements the one-person plan of `research/audit/research_audit.md` §4.6 (RA) and actions 16 and N13 of `research/audit/fresh_eyes.md` (FE), scoped to Tier A of `eval/EVAL_PLAN.md`. Binding decision rules are in `eval/prereg.yaml` (H9, H10 and the grader block); this file says what the rater does, in what order, with which instructions, and how the labels are used.

**Rater.** One person: the project owner, who is also the developer. There is no second human. Every agreement figure below is therefore human-vs-instrument or (Tier B) intra-rater, never human-vs-human. This is disclosed as limitation L34 (`research/methodology/README.md` §9).

**Session rules.** No session longer than 90 minutes; at most 4 hours of labelling per day; a break of at least 10 minutes between sessions. Record start and end times on the sheet. Fatigue degrades labels, and the timings re-calibrate this plan.

## 2. Blinding rules

1. **SIT key first.** T1 is finished, saved and hashed (`sha256sum`, hash committed) before the rater sees any model output about the SIT document: no agent run, no B0 run, no Claude chat answer about it, and no re-reading of `research/grading/worked_examples.md` §6 (the illustrative key K1-K10, traps T1-T6, no-change areas N1-N3, written by the agent's model family). The first agent run on the SIT document waits for the hash commit (`EVAL_PLAN.md` §1.7).
2. **Onboarding after T1.** T2 includes `worked_examples.md`, so it happens after T1.
3. **Condition-blind.** Every sheet (T4, T5, T6b, T7) strips run ID, condition, model name, cost, timestamps and the instrument's own label or score. Items carry opaque random IDs. A script (`eval/labelling/make_sheet.py`, to be built) shuffles with a recorded seed; the seed and the ID map stay in a file the rater does not open until the sheet is complete.
4. **Instrument-blind.** The rater never sees the matcher's score, the LLM adjudicator's class or the LLM grader's scores for an item before that item's label is saved. Completed sheets are hashed and committed before any comparison is run.
5. **Key sign-off before outputs.** For S-heldout, T6a happens in the access-1 session after the frozen agent's runs and before the rater looks at any output; outputs remain unopened until the T6a file is hashed.
6. **SIT v2 is held out from tuning.** The owner writes T8 without a coding-assistant session, does not paste it into any LLM session before line A-7, and makes no prompt or config change motivated by its content. The gold diff is hashed before any agent run on it.
7. **No re-labelling to raise agreement.** Labels, once saved, are never edited after comparison. Mistakes found later are logged as such, and the original label is the one used.

## 3. Labelling tool

A single HTML or CSV sheet per task, generated by script. Each row shows only what the task needs (below), a free-text note field, and a "cannot decide" flag (counted, not dropped). The document text shown is the canonical `doc.pages.txt` with page markers, the same text every verifier uses (ADR-006). Labels are saved as CSV, one file per task, with the rater, date and session times in the header.

## 4. Task instructions

### T1 Independent SIT key (3.5 h, time-boxed)

1. Read the SIT sample PDF from start to end once (about 60 minutes).
2. List every issue you would raise as a strict reviewer: strengths, risks, gaps, ambiguities, unresolved assumptions and validation needs (lab §2.3). For each, record in the canonical key fields (`spec/answer_key.schema.json`, enums from `spec/taxonomy.yaml`):
   - `id` (H01, H02, …), `kind`, `category`, `severity` (critical / high / medium / low, using the anchors in `spec/taxonomy.yaml`), `confidence_in_item` (sure / probable)
   - `location`: section(s), requirement IDs, page, and an `anchor_quote` of at least 8 tokens copied from the document
   - `description` (2-3 sentences) and **`core_insight`**: the one proposition a finding must state to count as detecting this item
   - `needs_external_research` (true/false) and, if true, the external fact you believe applies and your confidence in it
   - `expected_disposition` (`refinement_now`, `needs_investigation`, `needs_prototyping`, `needs_testing`, `governance_decision`, `no_change`)
3. List the sections you judge sound (`sound_sections`, each with `why_sound`) and the confirmed decisions you think should not be reopened without new evidence (`approved_decisions`).
4. Stop at 3.5 hours even if unfinished; record that it was time-boxed. Save, hash, commit the hash. Store the key outside every agent-readable path (for example `eval/real_dev/sit_key.owner.json`; the agent's allow-list excludes `eval/`).
5. Only after the hash is committed: convert the illustrative K-items to the same schema (a script may do this) for the comparison in §6.

### T3 and T6a `core_insight` sign-off (2 min per flaw)

A Claude session drafts each `core_insight` from the flaw's description and credit items (RA action 8). The rater accepts, edits or rejects each one against these tests:

- It is **one proposition** that names the defect, not the topic (an invented example: "the 6-hour batch window is longer than the stated 4-hour recovery point objective, so a failure late in the window breaks the objective" rather than "backup scheduling needs more detail").
- A generic finding that would apply to any design cannot satisfy it.
- It does not require particular wording, and it is consistent with the flaw's `credit.mode` (`all_of`: every required item is implied; `any_of`: the minimum count is implied).
- The location and anchor quote exist in the document text.

Record `accept / edit / reject` and, for an edit, the new text. Signing sets `scored_run_ready: true` together with the signer and date. This makes the rater the second reviewer that RA L12 requires (FE N12).

### T4 Matcher validation pairs (100 pairs)

**Source.** Candidate pairs from the pilot runs (line A-2: FULL and B0 on the 3 S-dev v1 documents), drawn from the matcher's candidate set (location overlap ∪ listwise shortlist ∪ embedding top-3). Sampling is stratified by the matcher's hidden score so that at least 35 pairs are likely matches (score 2-3) and at least 30 are likely non-matches, across all 3 documents and both conditions. Five pairs are repeated at random positions to measure within-session consistency (not counted in the 100).

**Each row shows.** The flaw: description, `core_insight`, credit items with roles, location. The finding: statement, `doc_anchors` with quotes and pages. The document text of the cited sections.

**The rater gives.** A score 0-3 using §5.1, plus two booleans, `core_insight_present` and `location_ok`, and an optional note.

### T5 Grader calibration, smoke tier (5 reviews, 25 min each)

Five reviews of the **SIT sample** (the document the rater knows best after T1), as `research/grading/README.md` §7 specifies:

1. a strong review: the best FULL review of the SIT sample from development runs (line A-1);
2. a mediocre review: a B0 review of the SIT sample;
3. a heavily padded review: review 1 plus 10 generic findings from the B-gen list and restated background, built by script (V2);
4. a terse but correct review: review 1 cut to its 4 most material findings, 2 no-change justifications, the verdict and the unresolved list, built by script (V3);
5. a review with injected errors: review 1 with one fabricated citation, one false-gap claim and one wrong page, built by script; the injection list is kept from the rater (V4/V5).

Order randomised. For each review, score D1-D10 on the 0-4 anchors of `research/grading/README.md` §3.2 (give the lower score when between anchors), flag every hallucination with its type from §4.3 and whether it is material, and record pass/fail after the gates of §4.2. The harness computes S; the rater does not.

### T5b R_base (30 min)

Take the best FULL SIT review and edit it by hand into a competent review that scores about 3 on every dimension (S ≈ 75), as `research/grading/README.md` §8 requires for V1, V4 and V10. Record what was edited (provenance; RA §4.5).

### T6b Adjudication review, S-heldout runs only

**Queue.** From every S-heldout run (FULL, B0, B0-$): 100 % of findings that the LLM adjudicator labelled VALID_UNPLANTED or HALLUCINATED, plus a seeded random 20 % of the other unmatched findings (MM §2.3 step 4). The LLM label is hidden. If the queue exceeds 120 items, a seeded random 120 is drawn from the VALID_UNPLANTED and HALLUCINATED group and the sampling fraction is reported (pre-registered, not a deviation).

**Each row shows.** The finding with its anchors, the cited document text, a search box over `doc.pages.txt` (for absence claims), and the key's flaw list and `still_valid_observations` for that document.

**The rater gives.** One class from §5.2. For HALLUCINATED, the type (fabricated quote, wrong location, false absence, misreading).

On S-dev runs the LLM adjudicator's labels stand without human review, and are labelled that way in the report.

### T7 Grader sample from the frozen agent (5 reviews)

A seeded random draw from the frozen-agent reviews, stratified: 2 FULL on S-dev, 1 B0 on S-dev, 1 B0-$ on S-dev, 1 FULL on the SIT sample (line A-6). S-heldout reviews are excluded so the rater does not read held-out documents in full. Same instructions as T5.

### T8 SIT v2 fixture (authoring, 3 h)

Write v2 of the SIT sample to FE R-06: some T1 items fixed, some partly fixed, one claimed as fixed in a change log or "comments addressed" table but not fixed, one regression introduced by a fix, one new section, an appendix of embedded reviewer comments (some correct, one wrong), and a cosmetic repagination. Write the gold diff (per item: fixed / partly fixed / claimed-not-fixed / persisted / introduced; changed and unchanged sections) before any agent run on it. Hash both.

## 5. Codebook

### 5.1 Match score (T4; `research/methodology/metrics.md` §2.2)

| Score | Label | Rule |
|---|---|---|
| 3 | MATCH | Same underlying defect; the `core_insight` is explicitly stated; the location overlaps the flaw's sections or requirement IDs, or a section that explicitly cross-references them |
| 2 | PARTIAL | Same defect, but the core insight is only partly stated, or the location is missing or vague |
| 1 | RELATED | Same area or topic, but a different or generic defect |
| 0 | UNRELATED | No relation |

Edge cases:

- **Topic without defect** ("the policy engine needs more detail") → 1.
- **Consequence without cause**, where the core insight is the cause → 2.
- **Correct defect, finding cites only a section that does not mention or reference the flaw's location** → 2.
- **No location at all** → at most 2.
- **`all_of` credit with one required item missing** → 2.
- **One finding covering two flaws** → score each pair on its own merits; the one-to-one assignment is done later by code.
- **Severity or category differs from the key** → ignore; matching ignores labels.
- **Hedged wording** ("may not handle…") that still states the core insight → 3.
- **Recommendation text that implies the defect without stating it** → 2.
- **Finding presents the design's own pending-backlog item as a discovery** → score the match normally and add the note "self-critique"; the grader handles the credit question.

### 5.2 Adjudication classes (T6b; `metrics.md` §2.3 step 4)

| Class | Use when |
|---|---|
| DUPLICATE | It restates a finding already matched, or another finding in the same review |
| VALID_UNPLANTED | Correct, specific and grounded in the document, and not in the key. If it sits in a section the key calls sound, still use this class and note "key error" (MM §6.2) |
| HALLUCINATED | Its central premise about the document is false: a quote not in the text, a wrong section or page, an absence claim refuted by a search of `doc.pages.txt` (try the term and two synonyms), or a misreading |
| NON_SPECIFIC | Generic advice that would apply to any design |
| INVALID_OPINION | Grounded, but the claimed problem is technically wrong, or it criticises a choice the document justifies |
| OUT_OF_SCOPE | About something the document explicitly puts out of scope |

When two classes fit, use the first one in this order: HALLUCINATED, DUPLICATE, OUT_OF_SCOPE, NON_SPECIFIC, INVALID_OPINION, VALID_UNPLANTED.

### 5.3 Rubric (T5, T7)

`research/grading/README.md` §1 (principles), §3 (weights and the 0-4 anchors for D1-D10; D11 only in delta mode), §4.2 (gates), §4.3 (hallucination types). Reconciled vocabulary per the note in §3.2 there. Strict marking: between two anchors, give the lower.

## 6. How agreement is computed

| Comparison | Statistic | Unit and CI | Report also |
|---|---|---|---|
| Matcher vs rater (H10) | Cohen's κ on the binary decision MATCH (3) vs not | 100 pairs; bootstrap over flaws (pairs are nested in flaws), 10,000 resamples | Quadratic-weighted κ on 0-3; confusion matrix; percent agreement; Gwet's AC1 if more than 70 % of pairs are non-matches; the share of rater-confirmed matches the matcher also scores 3 |
| Within-session consistency | Agreement on the 5 repeated pairs | count | — |
| LLM adjudicator vs rater (T6b) | Cohen's κ over the 6 classes, and κ on the binary "counts as correct for adjudicated precision" | reviewed items; bootstrap over findings | Confusion matrix |
| LLM grader vs rater (T5 + T7) | Quadratic-weighted κ over the paired dimension ratings (10 reviews × 10 dimensions = 100 pairs); ordinal Krippendorff's α | bootstrap over reviews | `research/grading/README.md` §7 table: exact and within-1 agreement, mean signed difference per dimension, mean absolute difference of S, pass/fail agreement, hallucination-flag precision and recall, Spearman ρ on S (report only) |
| Rater vs illustrative SIT key (T1) | Overlap counts: both, owner-only, illustrative-only | items | Chapman's estimate as a lower-bound indicator (MM §9) |
| Agent vs rater's SIT key (H9) | Recall against the owner key, by severity | 3 runs | Model-only findings adjudicated by the rater with §5.2 |
| Intra-rater (Tier B) | Cohen's κ, first vs second label on 40 pairs, ≥ 7 days apart | 40 pairs; bootstrap | Substitute ceiling for human-human κ (RA §4.6) |

Implementation: `sklearn.metrics.cohen_kappa_score` (with `weights="quadratic"` where stated); Krippendorff's α from a vetted package cross-checked once against a hand computation (`metrics.md` §11). The comparison script runs only on hashed, committed label files.

Interpretation tiers: κ (or α) ≥ 0.80 validated; 0.60-0.80 tentative, with the value printed beside every number the instrument produces; below 0.60, §7 applies. For the grader, the tier names of `research/grading/README.md` §7 apply (smoke at n = 5, tentative at n ≥ 20 with ordinal α ≥ 0.667); Tier A reaches at most "smoke plus a 5-review sample".

## 7. What to do if κ < 0.6

The rule in every case: fix the instrument or the codebook wording, never the labels; re-validate on **fresh** items, never on the ones used to diagnose; allow **one** revision round only, so the instrument is not tuned to one person's labels; log every version with its prompt hash.

**Matcher (H10).**
1. Read the disagreeing pairs and the matcher's rationales. Classify each disagreement: codebook ambiguity, matcher leniency (scores 3 where the rater gave ≤ 2), matcher strictness, or a bad `core_insight`.
2. If the cause is a bad `core_insight`, correct it (S-dev keys only; this is part of T3) and re-score those pairs.
3. Otherwise revise the matcher prompt once and validate on 50 fresh pairs from the pilot (about 1 h of extra labelling).
4. If κ is still below 0.60: matcher numbers are reported as "unvalidated" for S-dev, and **S-heldout matching is done by the rater** for FULL and B0 (about 12 runs × 14 flaws × 2 candidates ≈ 340 pairs, about 4.5 h), with B0-$ matched by the matcher and labelled unvalidated. H1 is then tested on human-matched S-heldout data plus matcher-matched S-dev data, and this is reported as a pre-registered fallback, not a deviation.
5. If the B-gen floor fails (strict recall > 0.05), the matcher is lenient regardless of κ: revise before any matcher number is reported.

**LLM adjudicator.** Rater labels already replace LLM labels for VALID_UNPLANTED and HALLUCINATED on S-heldout. If κ < 0.60, extend rater review to 100 % of unmatched findings in the S-heldout FULL and B0 runs (about 1.5 h more), and report S-dev precision as "LLM-adjudicated, unvalidated".

**Grader.** Follow `research/grading/README.md` §7 step 6: find the dimensions that disagree, fix the anchor wording or the prompt, re-run on 5 new reviews. If still below 0.60, grader scores are reported only as "illustrative, unvalidated". No Tier A claim depends on the grader, so no claim is lost.

**Intra-rater (Tier B).** κ < 0.60 between the rater's own two passes means the codebook is not stable. Revise §5.1 with the disputed cases, and downgrade every matcher-validation statement to "tentative" whatever the matcher's κ.

## 8. Data handling

- Label files, the SIT key and the SIT v2 fixture stay on the owner's laptop and in the private repository, outside every agent-readable path; only their hashes appear in logs.
- SIT material is not sent to a third party (a peer rater, or a second LLM provider used as a grader) without SIT's written agreement (FE R-10). Until then the second-provider grader scores only synthetic and held-out reviews.
- Rater identity in the report: the owner, named as the project author.

## 9. Consent and ethics (proportionate to one volunteer rater who is the owner)

This is not research on human participants: the only person labelling is the investigator, labelling artefacts they own or were given for the lab, and no personal data about anyone is collected beyond session times. No ethics-board review is sought. The points that still matter, recorded so a reader can check them:

1. **Voluntary and self-directed.** The owner chooses to label, sets their own schedule within §1's session rules, and may stop at any time; a stopped task is reported as incomplete, not hidden.
2. **What is published.** The labels, the agreement statistics and the owner's name as rater may appear in the submission to SIT. Raw labels stay in the private repository.
3. **Conflict of interest (L34).** The rater wrote the agent and the prompts and benefits from good results. Mitigations: the blinding rules of §2, labels hashed before comparison, the no-edit rule, the pre-registered fallbacks, and this disclosure in the report. Readers should weigh human-validated numbers with that in mind.
4. **Workload.** About 18 hours for Tier A, in sessions of at most 90 minutes.
5. **Third-party material.** SIT Internal material is handled under §8.
6. **If a peer rater is added later** (Tier C), they get a one-paragraph statement before starting: what they rate, how long it takes, that their labels and agreement figures may appear in the submission, whether they are named, that they may withdraw, and that they see SIT material only with SIT's agreement (FE R-11).
