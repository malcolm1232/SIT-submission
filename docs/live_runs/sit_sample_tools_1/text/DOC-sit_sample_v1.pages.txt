SIT Institutional Memory Platform - Detailed Design
1. Purpose and Scope
This document describes the architecture of the SIT Institutional Memory Platform - a governed memory
infrastructure for all AI agents serving SIT learners. It is written to a level of technical detail sufficient for an
engineering team, or an AI coding assistant working from this specification, to begin implementation. Section 28
gives an explicit, honest assessment of where that is and is not yet true.
This is not a per-agent memory store. It is an institution-level platform that provides:
● A structured memory namespace per learner, organised by life area and academic domain
● Policy-enforced access control - pre-retrieval, not post-filter
● A full administrative control plane (MMP) for configuring, governing, and auditing memory
● Audit trails for every operation - required for PDPA compliance
● Strict domain isolation (counselling memory is never readable by the advisory agent)
● Async write path and cached read path for scale
In scope
Memory infrastructure for AI Tutor, AI Buddy, Academic Advisory, Counselling, Career, and Orientation agents
serving ~15,000 SIT learners.
Out of scope
SIT-AI-Factory-RAG (the Azure AI Search RAG project) - a separate system, in a separate resource group, with
no shared infrastructure.

3. Foundational Principles
These ten principles govern every design decision in the platform, from the schema of a single table to the shape
of the Admin API. Where a later section appears to conflict with one of these, the principle wins.
Learner namespace is authoritative - the agent's copy is backup only. Conflicts are resolved in favour
P1
of the learner namespace.
Private by default - memory is private to the learner, shared by exception, anonymised for service
P2
learning.
Pre-retrieval access control - the namespace restriction gates the query itself, not the results after
P3
retrieval.
Counselling hard wall - wellbeing/counselling/ is HIGHLY_RESTRICTED. Zero cross-domain reads. No
P4
MMP override. No exceptions.
Cross-agent sharing via namespace only - agents never access each other's memory directly; the
P5
learner namespace is the only authorised bridge.
P6 No uncontrolled self-writing - all writes are classified and policy-checked before storage.
Audit every operation - access, write, denial, compaction, deletion, escalation are all logged. Required
P7
for PDPA.
P8 Write async, read cached - write via Kafka (non-blocking); read via Redis L1 → PostgreSQL.
Institution configures structure - slot templates, sensitivity levels, and retention rules are configured
P9
by administrators, not agents.
Minimum useful context - summary over transcript, fact over full conversation, token-budgeted
P10
context pack.

ever touches a data store directly.

14. Interaction Flow
Every agent-learner interaction, regardless of agent or learner, follows the same six-phase flow.

1. Auth check (Gateway)
- Agent registered in agent_registry?
- Learner authenticated? Token status?
- Slot access permitted for this operation?
2. Context assembly -- priority order:
Source 1: Learner namespace (authoritative -- if token ACTIVE)
Source 2: Agent global (always loaded)
Source 3: Agent per-learner backup (fills gaps; backup only)
Conflict resolution: learner namespace always wins.

3. Context pack built:
- Relevance-ranked (vector similarity)
- Recency-weighted
- Memory-type weighted (semantic > episodic > procedural, typically)
- Token-budgeted (minimum useful context)

15. Memory Access Gateway
Pre-retrieval checks are executed in order. Any failure denies the request and logs the reason. There are no
silent errors.
Check 1 -- Agent registered?
Is agent_id in /institution/sit/agent_registry/?
FAIL -> denied. Unknown agent cannot access any memory.
Check 2 -- Learner authenticated?
Is learner_id + auth token present in request?
FAIL -> denied. Cannot access learner memory without identity.
Check 3 -- Token valid?
ACTIVE -> proceed
EXPIRED -> prompt learner to re-authenticate.
Continue session using agent backup (degraded mode).
Log: re-auth required.
REVOKED -> inform learner (token revoked, contact support).
Agent backup only. No re-auth path.
Log: access attempt on revoked token.
Check 4 -- Slot exists in learner's namespace?
Exists -> proceed
Not exists + auto-provisionable slot type -> MMP provisions slot, proceed
Not exists + invalid slot path -> denied. Log: unknown slot.
Check 5 -- Agent permitted for this operation on this slot?
Read permission != Write permission (checked separately)
FAIL -> denied. Log: permission violation.
Check 6 -- Sensitivity clearance?
HIGHLY_RESTRICTED slots: hard block for all agents not in an
explicit named_agents list. No override. No exception.
FAIL -> denied. Log: sensitivity clearance failure.
The six ordered Gateway checks (Section 15 implements FR-4).
Access control is pre-retrieval. The namespace check gates the query itself - not the returned results.
16. Policy Engine
Seven policy dimensions are evaluated on every operation (this section implements FR-8):
Dimension Question
Storage Is this content allowed to be remembered at all?
Sensitivity Is this confidential, personal, regulated, or restricted?
Retention How long should this memory live? When does it expire?
Recall Can this specific agent/user retrieve this memory at this time?
Redaction Should part of the memory be masked before serving to this agent?
Deletion Can this be forgotten or purged on learner/admin request?
Purpose Is this memory being used for its original allowed purpose?

17. Memory Router - Five Components
All memory operations flow through the router. No agent touches a store directly.
[1] Gate
The Memory Access Gateway checks from Section 15. Executes first on every request.
[2] Validator (write path only)
Validates the write request against the slot template before any storage occurs.
- Is this key defined in the slot template for this slot_path?
Strict mode (prod): unknown key -> REJECT
Lenient mode (dev): unknown key -> WARN + log + surface in MMP dashboard
- Is the memory_type declared consistent with this key's type in template?
Mismatch -> REJECT
- Is the declared sensitivity within the slot ceiling?
e.g. writing HIGHLY_RESTRICTED to an INTERNAL slot -> REJECT
- Template version: validate against current published template version
Validator logic. Controlled by the MEMORY_STRICT_MODE=true/false environment variable (implements FR-11).
[3] Embedder
Generates vector embeddings for semantic memory operations.
Runs on:
- Write (semantic / procedural memory) -> store vector with record
- Semantic search (read) -> generate query vector before search
Skips on:
- Exact key lookup (key= specified, no vector needed)
- Episodic event writes (not vector-indexed)
- Meta-memory writes
Model: Azure OpenAI text-embedding-3-small (1536-dim)
Fallback path (embedding service unavailable):
- Flag record as unembedded (embedded: false)
- Fall back to BM25 keyword search for retrieval
- Add to MMP ingestion backlog for re-embed
- Log: embedding failure
[4] Dispatcher
Routes the operation to the correct store type and store instance.
Route by memory type:
WORKING -> In-memory store (no persistence, no Kafka)
EPISODIC -> PostgreSQL event table

SEMANTIC -> PostgreSQL vector table (pgvector)
PROCEDURAL -> PostgreSQL vector table (pgvector)
META -> PostgreSQL document table
Route by sensitivity tier:
PUBLIC + INTERNAL + RESTRICTED -> memory_standard schema
HIGHLY_RESTRICTED -> memory_sensitive schema (separate credentials)

Logs every operation. Non-negotiable for PDPA compliance (implements FR-13).
Every log entry contains:
agent_id, learner_id, slot_path, key, operation_type,

Logged operations:
- Every read (including cache hits)
- Every write (including async Kafka enqueue)
- Every denial (with reason)
- Token validation outcomes
- Slot provisioning events
- Compaction and deletion events
- Escalation writes and reads
Audit logs are append-only. Never modified. Retained per PDPA requirements.
18. Separate Read and Write Paths

<- Agent receives immediate ACK -- non-blocking

Write Consumer (background worker)

embedding, SIS sync) read the same event stream; separate topics per sensitivity tier keep HIGHLY_RESTRICTED
writes physically isolated in transit.

What is genuinely novel
The following have no direct precedent in open-source tooling:
● Learner memory namespace - a structured address space organised by life area, academic domain, and
stackable modules.
● Slot templates with SIS-triggered provisioning - namespace slots auto-created on enrolment events.
● Pre-retrieval access control - the namespace restriction gates the query, not the results.
● Counselling hard wall - an architectural constraint with no MMP override path.
● Cross-agent sharing via namespace only - no direct agent-to-agent memory access.
● Two-tier sensitivity store with separate credentials per tier.
● Escalation slot semantics - write-only for the triggering agent, read-only for the target domain.

Overall conclusion
An AI coding assistant working from this document could reliably generate, with little or no clarification needed:
the database schema and migrations, the YAML slot templates, the Gateway middleware, and the

Before an AI coding assistant could generate the remaining components without inventing unstated design
decisions, three specification gaps should be closed first:
● A Policy Engine decision table or pseudocode - precedence rules across the seven dimensions, expressed as
an explicit algorithm or truth table, not just seven named questions.
● MMP Admin API request/response schemas - JSON Schema or Pydantic-model-level detail for every
endpoint in Section 21, including error responses and the Admin API's own auth model.
● A MemoryClient SDK interface specification - method signatures, parameter types, error/exception model,
and at least one worked example per memory type.
Recommendation: treat this as the first deliverable of Build Phase 3 (Policy Engine) and Build Phase 7
(MemoryClient SDK) - close these three gaps in a short, focused specification pass before generating code for
those components. The remaining Pending Backlog items (cohort namespace, compaction, non-SIT identity) can
reasonably be deferred to a later build phase, as they are not required for the initial six agents' launch scope.
