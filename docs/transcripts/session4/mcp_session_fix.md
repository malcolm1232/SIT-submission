## What changed

1. Session recovery (`6923a69` interface change, `7678db2` behaviour).
   A closed session (MCP error -32000, a closed or ended stream, a reset connection) on an established session is now `session_closed`, not `tool_error`.
   The gateway reopens the session once with a new `initialize` and the same key, then repeats the call once; only a second failure counts against the tool.
   When several concurrent calls meet the same dead session, as the run's five web searches did, they share one reopen.
   A session idle longer than `tools.session_idle_reopen_s` (60 s, in `config/tools.yaml` with a comment citing the run and the probe) is reopened before the next call, never while a call is in flight.
   Each reopen is a progress line, an entry in `MCPToolGateway.session_events` and the message of the call's attempt in `tools.jsonl`; it is not a degradation.
2. Disable rule (`3488d81`).
   A tool is disabled for the run only after two genuine failures in a row: a tool error from a live session, or a call that met a closed session again after the reopen.
   The disclosure names the counts: genuine failures, tool errors, failures after a reopen, calls, and session errors recovered.
3. Tool-error disclosure (`b86cbcb`).
   When research ends, each `tool_error` degradation states the calls attempted and failed, the error classes, the last error, whether the tool was disabled, and the unanswered questions of its capability.
   The run's DEG-002 would now read "5 of 5 call(s) failed (...)" with the unverified question IDs, instead of "that call contributed no evidence".
4. Research stop reason (`52f83b0`).
   A model stop vote reports `sufficient_evidence` only when at least one question was answered.
   Otherwise it reports `tool_failure` when every call failed or an offered tool was disabled (the detail names the tool), and `no_marginal_gain` when the tools worked and answered nothing.
   This is stricter than the brief's "an answer or new external evidence", because the run's one scholarly call added 10 ledger entries, so that rule would have kept its reason.
   No enum value was added; the brief's `no_usable_tools` and `model_stopped_early` map to the existing `tool_failure` and `no_marginal_gain`.
5. `report.md` (`c9f6540`).
   A severity count in the verdict prose ("seven high-severity") is rewritten to the findings' own count, in the prose's style; `report.json` keeps the model's text.
   The document version is stored without its word prefix ("Version 2.0" becomes "2.0") and shown as "v2.0", also for runs recorded before the fix.
   Bullet and numbered lists are kept in the verdict rationale, its conditions, "What would change this verdict", finding and intent statements, and the recommendation and no-change texts.
   Tests pin all three on the committed `report.json` of the run and on the example Review fixture.
6. Replay (`d23af50`).
   The run's recorded tool results replay as recorded: the five `search_web` failures come back as the recorded `tool_error` with the -32000 message, because replay serves `tools.jsonl` without running the tool policy again.

## Design gap for the planner (defect 7, not changed)

The four assess shards start at about 2 s, while research starts after understand at about 126 s, so no shard can use external evidence.
Only refine and the verdict call see it: in the run, the one cited external entry (EV-002 in FND-026) was added by refine to a finding a shard had already drafted.
Closing the gap means either starting research before the shards (at the cost of stage-1 wall time) or a second evidence pass for the shards, which is a stage-order decision in `orchestrator.py` outside this branch.
The idle reopen also matters more under the current order: the warm-up opens the sessions at about 2 s and research first uses them about two minutes later.
