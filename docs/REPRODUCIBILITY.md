# Reproducibility policy

Date: 2026-10-02. Resolves audit items C15, C16, C28, U5 and P0 item 6 (`research/audit/research_audit.md`). Applies to every run of the agent and every run of a measuring instrument (matcher, judges, grader). Model facts were checked against the `claude-api` skill (model table cached 2026-09-25). Related decisions: `docs/DECISIONS.md` ADR-002 (all Opus 5.5), ADR-006 (ingestion), ADR-007 (anchoring), ADR-008 (where things run).

## 1. What this policy can and cannot promise

Claude Opus 5.5 exposes **no sampling controls**. `temperature`, `top_p` and `top_k` are rejected with a 400, there is no `seed` parameter in the Messages API, and thinking cannot be switched off (only `output_config.effort` is adjustable). Two runs of the same request can differ.

So reproducibility here means:

- **Bitwise** for everything downstream of the model: given the recorded model responses and tool results, the report, the anchors, the ledger and every metric are regenerated byte for byte.
- **Statistical** for the model itself: a re-execution reproduces the *distribution* of results, which is reported as k runs with confidence intervals, not as a single number.

The write-up says this plainly: results are statistically reproducible, not bitwise reproducible at the model.

## 2. Pinned model ID

- The model is `claude-opus-5-5` for every agent call (ADR-002). The skill's model table lists no dated snapshot for it; the bare ID is the most specific pin that exists.
- It is set in exactly one place, `config/agent.yaml`, and echoed into the manifest.
- Once per run, the agent calls `client.models.retrieve("claude-opus-5-5")` and stores `id`, `created_at`, `max_input_tokens` and `max_tokens` in the manifest.
- Every response's `model` field is logged per call in `llm.jsonl`. The manifest field `served_models` is the set of those values. In eval mode a run whose `served_models` is anything other than `{"claude-opus-5-5"}` is **invalid** and is excluded (and reported as excluded).
- Anthropic can update the model behind an ID without changing it. That residual drift is disclosed as a limitation (methodology L31), and eval conditions are interleaved in time so that any drift does not line up with a condition.

## 3. No silent fallback

- **Eval, dev and rehearsal runs send no `fallbacks` field** and no `server-side-fallback-*` beta. A classifier refusal (`stop_reason: "refusal"`, HTTP 200) is handled by the agent: check `stop_reason` before reading `content`, retry once with professional-review framing, and if it persists mark that section "model declined" and continue (robustness LLM-06). Every refusal is recorded with its `stop_details.category`. Details from the `claude-api` skill that the gateway must respect: branch on `stop_reason`, never on `stop_details` (the category can be `null`, which is a valid state); a refusal can arrive before any output (empty `content`) or **mid-stream**, in which case the partial output is discarded, never parsed; classifier declines and the model's own refusals both surface as `refusal`; a refusal still counts against rate limits. The skill documents no prompt change that avoids Opus 5.5 false positives, so the reframed retry is our heuristic and its success rate is reported, not assumed.
- **The LLM gateway never switches model on its own.** On 429 it honours `retry-after`; on 529/503 it backs off with jitter; after the retry budget it writes a checkpoint and exits with the documented "LLM unavailable" exit code so the run can be resumed (robustness LLM-01 to LLM-03). The SDK's built-in retries are disabled (`max_retries=0`) so attempts are counted in one place.
- **Demo-only opt-in.** `--allow-fallback` (or `allow_fallback: true` in `config/agent.yaml`) sends `fallbacks: "default"` with beta `server-side-fallback-2026-07-01` on `client.beta.messages`. On a refusal the API re-runs the request on the model Anthropic recommends for that refusal category: targets come from `allowed_fallback_models` on `/v1/models` (expected `claude-opus-5`, `claude-opus-4-8`), the routing is not published, `reasoning_extraction` declines are not retried, the fallback model runs without Opus 5.5's thinking blocks, and if the fallback model is rate-limited the original refusal is returned with `stop_details.recommended_model`. So when it is used:
  - the manifest records `fallbacks: default`;
  - every call whose `usage.iterations` contains a `fallback_message` entry is listed in `model.fallback_events` with the from-model, the to-model (from `response.model`) and the refusal category;
  - the report's limitations section states that part of the review was produced by another model;
  - the run cannot be used as eval evidence.
- `fallbacks` is rejected on the Batches API, so batched instrument runs never use it.

## 4. Frozen prompts, config and schema, with content hashes

- **Prompts are files.** Every prompt lives in `prompts/*.md` and is rendered with Jinja `StrictUndefined` from declared variables only. There are no prompt strings inline in Python.
- `prompts/PROMPTS.lock` lists the SHA-256 of every prompt file; `prompts_bundle_sha256` is the SHA-256 over the sorted list of `(path, sha256)`. CI fails if the lock is stale. The rendered request body's hash is also logged per call.
- `config/*.yaml` files are hashed the same way, plus an `effective_config_sha256` over the merged config after CLI flags.
- The finding and report schemas (Pydantic, exported to JSON Schema) carry a `schema_version`; `eval/schema/taxonomy.yaml` is hashed.
- **Eval mode refuses to start** if the git tree is dirty, if `PROMPTS.lock` does not match, or if `prereg.yaml`'s hash differs from the one frozen before the held-out runs.
- A tag (`freeze/<date>`) marks the prompt and config state before any S-heldout access and before the Blind run. Changing anything after that is a recorded deviation.
- Nothing volatile (dates, run IDs, timestamps) goes into prompts or the cached prefix.

## 5. Structured outputs

- Every scored output (findings, verdict, triage, coverage map, report fields) is produced through `output_config.format` / `client.messages.parse()` against the versioned schema. The report document itself is rendered from those fields by a Jinja template; the model never writes the report structure.
- Constraints that structured outputs cannot express (at most 3 locations per finding, quotes of at least 8 tokens, non-empty rationale) are checked in code after parsing.
- `stop_reason: "max_tokens"` is detected before parsing. Truncated JSON is never repaired into a shorter valid object; the call is retried with a higher `max_tokens` or the work is split (robustness LLM-07).
- Native citations are not used for scored outputs because they cannot be combined with `output_config.format`.

## 6. Recorded calls and strict replay

Each run directory `runs/<run_id>/` holds:

| File | Content |
|---|---|
| `manifest.json` | Section 8 schema. Written before the first model call, finalised at exit |
| `llm.jsonl` | Every model request (body hash, plus the body itself minus the PDF bytes, which are referenced by hash) and full response: `model`, `stop_reason`, `stop_details`, `usage` (including `usage.iterations` and cache fields), `request_id`, latency, retries |
| `tools.jsonl` | Every MCP call: server, tool, canonical arguments, raw result, `isError`, latency, transport status, cassette key |
| `ledger.json` | Evidence ledger: stable IDs, source URL, retrieval time, the snippet as the agent saw it, its hash |
| `snapshots/` | Stored copy of every fetched page or paper the agent read |
| `doc.pages.txt`, `doc.sections.json` | Canonical text and section map (ADR-006) |
| `checkpoints/` | One JSON per completed stage (used by `resume`) |
| `report.json`, `report.md` | The output and its rendering |

Transports (`--transport`):

- `live`: real MCP servers, recorded to `tools.jsonl`.
- `record`: as live, and also writes redacted cassettes under `tests/robustness/cassettes/tools/<server>/<tool>/<sha256-key>.json`. Cassette key = SHA-256 of `server|tool|canonical_args` (keys sorted, whitespace collapsed, queries lower-cased, volatile fields dropped). Auth headers and keys never reach disk.
- `replay`: tools are served from cassettes. **Strict** mode (default for tests and eval) raises `ReplayMiss` on any unseen call and the run fails; **lenient** mode (exploration only) returns an empty result.
- LLM replay (`dra replay <run_id>`): model responses are served from `llm.jsonl`, matched by call index and request-body hash. A hash mismatch fails the replay. This re-renders a reported run offline with no API key, which also keeps results checkable after the SIT MCP key is revoked (audit §3, reproducibility row).

## 7. What "reproduce" means for an evaluator who clones the repo

| Level | Needs | Command (planned) | Pass criterion |
|---|---|---|---|
| **R0. Re-render** | Clone + `uv sync --frozen`. No API key, no network | `dra replay runs/<id>` for each run in `outputs/lab_session/` and `eval/results/` | `report.json`, `report.md` and the anchor table are byte-identical to the committed hashes in the manifest |
| **R1. Re-score** | Same as R0 | `python eval/score.py --runs eval/results/ --instrument-replay` | Every table in the results report is recomputed exactly from the logged runs and the logged instrument transcripts |
| **R2. Re-execute with recorded tools** | An Anthropic API key (`ANTHROPIC_API_KEY`); no SIT key | `dra review <pdf> --transport replay --k 3` on the same docs | All invariants INV-01 to INV-11 hold; each headline metric falls inside the reported 95 % CI. Calls the recorded cassettes cannot answer fail loudly in strict mode; lenient mode is allowed for exploration and labelled as such |
| **R3. Full live re-run** | Anthropic key + `SIT_MCP_API_KEY` + reachable SIT servers (may not exist after the evaluation period) | `dra preflight && dra review <pdf> --k 3` | As R2. External evidence will differ (search results change); differences are expected and do not count as failure |

R0 and R1 work in the cloud sandbox (ADR-008). R2 and R3 run on a machine with keys. The lab-session outputs (lab §5.1) are committed with their full run directories so R0 and R1 always work.

## 8. Run manifest schema

Written as `runs/<run_id>/manifest.json`. Fields marked * are required in eval mode. This replaces methodology §7.1's `temperature`, `top_p` and `seed` fields (audit C15).

```yaml
manifest_version: 1
run_id: uuid4                         # *
mode: eval | dev | rehearsal | demo | replay   # *
created_utc / finished_utc            # *
split: S-dev | S-heldout | Blind | Real-dev | OOD | rehearsal   # *
split_assignment_sha256               # *
prereg_sha256                         # * (eval)
condition: FULL | B0 | B0-$ | B-gen | A1 | A2 | A3 | A4e | A5   # *
k_index: 1..k                          # which of the k runs this is
previous_run_id                        # v2 re-review only
doc:
  id, sha256_pdf, pages, bytes        # *
  canonical_text_sha256               # *
  extractor: {name: pdfplumber, version}           # *
  normalisation_version               # *
  native_pdf_block: true | false      # false = text-only fallback, disclosed
code:
  git_commit, git_dirty               # * (dirty refused in eval)
  package_lock_sha256, python, os     # *
  anthropic_sdk_version, mcp_version  # *
prompts: {files: {path: sha256}, bundle_sha256}   # *
config: {files: {path: sha256}, effective_config_sha256, cli_args}   # *
schema: {finding_schema_version, report_schema_sha256, taxonomy_sha256}   # *
model:
  requested_model: claude-opus-5-5    # *
  models_retrieve: {id, created_at, max_input_tokens, max_tokens}   # *
  served_models: [..]                 # * set of response.model over all calls
  sampling: "provider-default (not settable)"   # *
  thinking: {type: adaptive, display: omitted | summarized}   # *
  effort_by_stage: {plan, research, assess, refine, verify, report}   # *
  max_tokens_by_stage                 # *
  betas: []                           # *
  fallbacks: none | default           # * (eval: none)
  fallback_events: [{call_id, stage, from_model, to_model, category}]
  refusals: [{call_id, stage, category}]
  sdk_client: {max_retries: 0, timeout_s}
tools:
  transport: live | record | replay-strict | replay-lenient   # *
  cassette_set_sha256                 # replay
  url_policy_sha256                   # *
  servers: [{name, enabled, url_sha256, allow_tools, protocol_version, tools_list_sha256, health_at_start}]   # *
stop:
  active_rules, params                # *
  stop_reason: sufficient_evidence | no_marginal_gain | budget_tool_calls | budget_tokens | deadline | tool_failure | error   # *
fault_injection: {profile: none | <scenario-id>, schedule_sha256}   # *
usage:
  calls, tool_calls                   # *
  input_tokens, cache_creation_input_tokens, cache_read_input_tokens, output_tokens   # *
  cost_usd, price_table: {source, date}   # *
timing: {wall_clock_s, per_stage_s}   # *
outcome: completed_nominal | completed_degraded | aborted_graceful | crashed | timeout | budget_exceeded   # *
degradations: [..]                    # every fault event disclosed in the report (INV-07)

```

Instrument runs (matcher, judges, grader) write a parallel `grading_manifest.json` with the instrument model, its settings (temperature only if a non-Claude provider accepts it), prompt hashes, sample seeds for finding shuffles, batch IDs and costs.

## 9. k-run reporting and pass^k

- **k per (doc, condition):** k = 3 by default; k = 5 for the primary FULL vs B0 comparison; robustness L1 k = 3, adversarial scenarios k = 5. Runs of different conditions are interleaved in time.
- **Report:** mean, between-run SD, the share of variance due to runs versus docs (ICC), and a 95 % CI from a bootstrap clustered by document. Never a single best run.
- **pass^k** (τ-bench): the probability that all k independent trials pass. With n ≥ k trials of which c pass, the unbiased estimate is pass^k = C(c, k) / C(n, k). Report it next to pass@k = 1 − C(n − c, k) / C(n, k). Both estimators get a hand-computed unit test before use (audit §2.2).
- **Safety criteria** (prompt-injection success, canary leaks, fabricated citations) need k/k.
- **Stability without a seed.** Robustness BEH-15 measures run-to-run stability directly: verdict agreement across the k runs, finding overlap (matched to each other with the methodology matcher), and the spread of each headline metric. It does not assume a seed or temperature 0 exists.
- A run excluded for any reason (invalid `served_models`, crash, dirty tree) is counted and reported, not silently replaced. Intention-to-treat and per-protocol figures are both shown (methodology §6).

## 10. Checklist before a run counts as evidence

- [ ] Clean tree; `PROMPTS.lock` matches; `prereg.yaml` hash matches the frozen one (held-out and Blind).
- [ ] `model.served_models == ["claude-opus-5-5"]`; `fallbacks: none`; no fallback events.
- [ ] `tools.transport` recorded; cassettes hashed if replayed.
- [ ] All `*` manifest fields present (INV-09).
- [ ] `llm.jsonl`, `tools.jsonl`, ledger and snapshots present, so R0 and R1 can be run by someone else.
